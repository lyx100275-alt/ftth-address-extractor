# 会话效率与中断处置（外移自 SKILL.md，2026-09-16）

> 触发场景：长任务（一张图从探查到出表）总耗时远超预期；或会话被上游中断后续做。

## 一、耗时去哪儿了（双会话实测）

| | 会话 A（凤鸣朝阳） | 会话 B（云峰） |
|---|---|---|
| 墙钟 | 92.9 min | 96.7 min |
| 工具执行 | 32 次 / **179.7 s（3.2%）** | 62 次 / **378.3 s（6.5%）** |
| 等用户回话 | **70.6 min** | **66.6 min** |
| 净执行 | 22.3 min | 30.2 min |

结论：**墙钟约 70% 是等用户回话**，工具执行只占 3~7%。
故提效第一杠杆是**减少人机往返**，而不是改脚本。

统计口径：取会话库中每条 part 的 `time_created` 毫秒戳；「工具调用→返回」配对累加为执行时长，
「用户消息→助手结束本轮」之间的间隔累加为等待时长。

## 二、三条纪律

### 1. 一次给全可执行命令，裁决项集中提交

探查一旦拿到参数，就连跑 `probe → plan → parse → inspect`，中间产物只落盘、不请示；
把「须人工裁决项」（楼号断号、覆盖冲突、双源不一致…）**攒到一处集中提交**。
反面样本：逐步骤请示，每步一次往返，一次往返 ≈ 数分钟。

### 2. 禁止反复自造探查脚本

实测会话 B 在跑 `plan` 之前用 **12 min** 写了 **9 个**一次性 `probe_*.py` 逐项手探
（图层 / 标题 / 编号 / 竖干 / 图标 / 总图…），而其后跑一条 `plan` 就**完整覆盖**了那些脚本的全部输出。

探查阶段只用技能自带命令：`probe` / `plan` / `count-box` / `dump_geom`。
确实需要临时脚本时，**先读 `<DXF>.geom.json`**（亚秒级），仍不够再写；
写完即用，**不得反复重写同类探针**。

### 3. 断流后开新会话，不要反复「点继续」

实测会话 B 三次断流被救活，累计 input 由 20 万涨到 **113 万** —— 因为**每次复活都要把全部
历史上下文重放一遍**，而进度净变化为零（始终在 Step 1b 打转）。

处置流程：

1. 上游 502 / `connectex` / `no such host` → **先重试一次**。
   多为瞬时抖动：实测事后复核 DNS 解析与上游链路（HTTP 200 / ping 19 ms）均正常。
2. 仍失败 → **开新会话**，把已定案的中间产物直接喂进去续做：
   `config.json`（probe 产物）/ `profile.json` / `parse.json` / `coverage.json` / `households_icons.json`。
   这些文件本身已含参数与结论，新会话无需重跑前序步骤。
3. 长任务（>30 min）建议**错峰单跑**，避免与另一长任务同时占用同一上游。

## 三、与其它纪律的关系

- 与「性能纪律」（同图只解析一次）互补：那条省的是**机器时间**，本条省的是**人的往返时间**。
- 与「探查纪律」（禁 shell 内联）互补：那条防**静默失败**，本条防**重复劳动**。

效率纪律实测依据（外移自 SKILL.md，2026-09-17）：两会话实测墙钟 93~97 min 中，工具执行仅占 3~7%，约 70% 在等用户回话；反复「点继续」使累计 input 由 20 万涨到 113 万而进度零净变化。
进度纪律实测教训（外移自 SKILL.md，2026-09-17）：todo 冻结在早期状态而实际工作已推进到尾声时，外部（用户/监控）无法判断真实进度，会把正常推进误判成停滞。


## 四、交付纪律

1. **覆盖既有交付物前先备份**。目标路径已有同名成品时，先复制到工作目录并加时间戳
   （如 `备份_<时间戳>_<原名>`）再覆盖；不得直接强制覆盖抹掉上一版。
   用户说「不参考历史产物」指的是不读它，不等于可以销毁它 —— 上一版成品仍可能被人工回滚比对。
2. **交付核验以「数据行数 + 内容指纹」为准，不以文件大小/mtime 为准**。
   Office 系编辑器（WPS/Excel）打开带 AI 生成内容标识的成品再保存，会**追加标识行并改写字节**：
   实测交付后数十秒内文件由 27,031B 变为 28,123B、mtime 前移，而业务数据一行未变。
   ⇒ 核验口径：读回成品统计「业务数据行数」与「关键列取值指纹」，与源一致即视为交付成功；
   size/mtime 只作辅助线索。
3. **复核交付结果要重读目标文件本身**，不要拿生成时刻的中间产物代替。
4. **产物必须是标准 JSON**（`.json` 内不得出现 `NaN` / `Infinity` / `-Infinity`）。
   Python 的 `json.dump` 默认把非有限浮点写成这三个字面量，而它们**不在 JSON 规范内**：
   严格解析器（JS / Go / 多数工具的默认实现）会因此**拒绝整份文件**，而不是跳过那个字段；
   而 Python 自己的 `json.load` 是宽容的 ⇒ **本机全绿、跨语言全线不可读**，属最易漏过出口的一类。
   语义上 `inf` 是「未测得」的占位垃圾值，写成它等于让垃圾值冒充测量结果。
   清洗后的 `null` 表示「本图未测得该量」，**与 0 不同**，消费方不得当 0 用。
   ⇒ **产出方**：写 `.json` 一律走 `ftth_common.write_json`（内置清洗，命中项登记、不静默丢）；
   ⇒ **出口闸门**：`ftth.py pipeline` 跑完自动扫产物目录，命中即把 rc 抬到 2（不得静默出关）。

## 五、图内矛盾：分级处置，不推理

**规则**（2026-09-17 用户指令）：图内、或图与表之间前后矛盾的地方，**不得自行推理判定哪一方正确**。
但与"发现即停机"不同 —— **闸门放在出口（成品），不放在入口（每一次比对）**。原则三句：

1. **发现要主动**：主动比对多处来源、扩大取证、归一化找差异。发现不了冲突才是失职。
2. **裁决交人工**：判定"哪一方对"一律交人，不得自行得出结论。
3. **成品零容忍**：中间产物可带标记继续；**未经人工裁决的值不得进入成品**。

### 5.1 先分三层：测量 / 表达层归一化 / 推理

作业按「对图纸做了什么」分三层。**层不同，权限不同**：

| 层 | 含义 | 是否受限 |
|---|---|---|
| **测量** | 对**图纸已载信息**的量化读取：按皮线米数跑 V 型 / 竖干断口取覆盖区间、用包围盒中心判标注与箱号配对、直读标注原文、几何坐标比对 | **不受限**，照常执行 |
| **表达层归一化** | 只改**表达**、不改**业务事实**、**不引入图上没有的数值关系**：`一层`/`1F`/`F1`/`1楼` → `1F`；`FX-01`/`1#FX`/`分纤箱1` → `FX01` | **可自动**，但须过下方三条硬边界 |
| **推理** | 推断图上没写、或需判断"哪一方像笔误"的结论 | **受限**，按 §5.3 交人工 |

**归一化的三条硬边界（缺一不可）**：

1. **不得引入图上没有的数值关系** —— 判据是「改写后，图上原本没有的**数量**是否出现」。
   反例：`*16` / `×16` / `X16` 这类**乘数标注不是归一化** —— 它把「图上 3 个图标」变成
   「该楼 48 户」，产生了图上没有的数值关系 ⇒ **一律按 §5.3 第④类报人**，
   不得因「它看起来就是个乘法、语义唯一」而自动展开。
   （实测：同一张图两版交付差 122 户，其中 120 户即由此而来。）
2. **须先证是同一物理体才能归组** —— 多个写法归为同一 `canonical_id` 之前，
   必须先证明它们指向**同一个物理设备**；判据限「坐标邻近 + 连线关系」两者，
   **二者均可外部复核**。位置或连接关系不同 ⇒ 不得归组，按 §5.3 第④类报人。
3. **只用于比对，不得回写为原始事实** —— 归一化结果可参与比对判定，
   但**不得覆盖或替代原始标注**写进任何产物。原始写法原样保留（落点见 §八）。

**算推理、禁用作裁决依据的四类线索**：

| 线索形态 | 为什么不能当判据 |
|---|---|
| 跨图惯例 / 全项目统计多数（"其余各处都这样"） | 惯例是**归纳**，证不了眼前这一处；多数一致还可能是同源同错 |
| 命名 / 编号规律（奇偶、序号递增） | 只是**约定的旁证**，不是图纸读数 |
| 图示自洽性（"这样画才对称 / 才合理"） | 工程合理性判断，属读图外推理 |
| "哪一方更像笔误"的整体观感 | 无判据的主观推定 |

### 5.2 归一化前置（防假阳性）

比对前必须先把**语义**对齐，否则写法差异会淹没真矛盾：

- 单位 / 写法 / 顺序 / 全半角 / 省略形式先归一（实测同一批图上米数存在 `20m*2`、`2Px2芯x36m`、`2芯x36m`、`36m` 四种写法，语义相同）；
- 同名要素须带足限定（多地块同名楼栋须带地块 / 区号）。

**归一化后仍冲突，才算矛盾**；归一化即消解的差异只记入比对日志，不上报。

**归一化与原始事实必须分开存**：归一化结果只用于比对与显示，**原始标注不得被改写覆盖**
（"图上原本写的是什么"在产物里要有落点，见 §八）。把归一化结果当成图纸原始数据，
会在返工复核时失去与图纸对话的能力。

### 5.3 分级处置（四类）

| 类 | 判据 | 处置 | 停机 |
|---|---|---|---|
| ① | 写法 / 单位 / 顺序不同，归一化后语义等价 | 视为一致，只记比对日志 | 否 |
| ② | **有客观判据**可判（几何位置 / 物理测量 / 唯一取数来源 / 标注原文直读） | **自行判定并留证**（属测量） | 否 |
| ③ | 无客观判据，但**只影响中间产物、不进成品** | 取安全侧（保守值或留空）＋ **显式标记**，随交付清单列出 | 否 |
| ④ | 无客观判据，**且要写进成品数值** | **停下，报人工核验** + 必给推荐与全选项 | **是（唯一）** |

- **第②类是"少问人"的主渠道**：有判据就有答案，不必报人；缺判据时才报。
- 第④类报人时按 **5.5** 改写问题，不要提交"请核查"这类把取证推回用户的问法。
- **第④类允许「先推理再推荐」，但推荐不得代替裁决**（2026-09-18 用户裁定）。**三道锁**：
  ① 推荐**只许出现在待确认清单的「参考线索」列**（L1-C5 四列表），**不得出现在任何数据列**；
  ② **禁止默认值 / 默认选项** —— 严禁「无人回复则取 A」（否则"交人裁决"退化为"人不出声即自动生效"）；
  ③ **必须列全所有选项** —— 推荐项只标倾向，不得因有推荐而省略其余选项。
- 裁定后 **锁**：结果锁定为基准值，后续只能新增、不能覆盖（同 `SKILL.md` L0-I4 ⑤）。

### 5.4 数据来源权威等级（**空表 = 一律按第④类**）

来源冲突若存在**项目方已声明的**优先顺序，则按该顺序裁决 —— **这是规则，不是推理**。
**未经声明前本表为空，空表即按第④类处理**（不因"缺表"而自行排定）。

| 等级 | 来源 | 状态 |
|---|---|---|
| 1 | 待项目方填写 | 空缺 |
| 2 | 待项目方填写 | 空缺 |

- **填写要求**：由用户 / 设计院**显式声明**，一经声明即锁定为基准。
- **禁止**由 Agent 依"惯例 / 多数"自行排定优先级 —— 那正是 §5.1 所禁的推理。
- 建议候选（**仅作提示，不构成默认值**）：设计院正式对应关系表 / 图纸专用标注 / 平面图箱位图 / 一般图面文字。
- 声明示例：`来源优先级：设计院对应表 > 图纸标注 > 平面图`。

### 5.5 报人时必须给"最小化二选一"

报人**不得把取证工作推回给用户**，须写成可直接作答的选择题：

- 反例：`1 号楼箱号可能有误，请核查。`（用户得自己翻图重查一遍）
- 正例：`图纸标注 4层→FL08FX02，平面图箱位图标 4层→FL08FX01，冲突且无客观判据，请确认以哪个为准。`

并且**批量提交**：攒到阶段末一次性报（见 §二·1 效率纪律），不遇一个停一个 —— 实测墙钟约 70% 耗在等用户回话，
逐条打断与该指标直接对冲。

### 5.6 三条底线（与流程效率无关，不可协商）

1. **不得静默择一** —— 不得由脚本自动取舍、取多数票、按惯例改写某一方。
2. **惯例 / 多数 / 命名规律 / 图示自洽性不得作裁决依据** —— 只算参考线索。
3. **未裁决的值不得进入成品** —— 第③类可带标记继续；第④类的冲突值**必须留空或标记，且相关部分视为未定稿**，
   并在交付说明显式列出"本次交付含 N 项未裁决冲突"。

**教训**：① **照抄源数据也是错误来源之一** —— 链路可复现、脚本无 bug，源数据本身仍可能错；
② **闸门要放出口** —— 把"发现即停"当铁律会与"减少人机往返"对冲，故停机只保留在第④类；
③ **底线 3 的前提是「疑点找得到该值」** —— 一条待裁决项若在机械判定上关联不到任何楼栋/单元/箱，
它就不会产生 pending，底线的执行变为空转（疑点列在清单里，值照样进成品）。
故登记疑点时**必须写明作用域**（对象串按 `楼栋 [单元] [编号]` 的段数分级），
且作用域判定全技能只允许一份实现 —— 复制必漂移。判据与实现见 SKILL.md L1-C8。

### 5.7 来源数与校验分流（2026-09-18 用户裁定）

矛盾的**前提**是"同一元素有多处来源"。**先数来源数，再决定要不要比对**：

| 可用来源数 | 处置 |
|---|---|
| **0 处** | 先自证「真的没有」（查过哪些图层 / 实体类型 / 坐标区 / 写法均无）→ 仍无则**待确认**。「**没找到」≠「图上没有」** |
| **1 处** | **直接采信**，但须过**总体核对**（见下）—— **单源 ≠ 免检** |
| **≥2 处** | 进 §5.2 归一化 → §5.3 分级处置；不一致按第④类报人（**可推理可推荐，不裁决**） |

- **单源值的替代校验 = 总体核对**：单源值虽无同元素第二来源，必须过**跨元素的结构校验** ——
  例如「某单元全部箱的覆盖楼层并集 = 该单元有户数标注的楼层集合」（覆盖完整性门禁，
  见 `coverage_rules.md`）。**单源与"已确认"效力相当，但依据不是"用户说过"，而是"系统自洽"**（见 5.8）。
- **计算孤立 ≠ 算不出来**：算得出但图上无标注可比 → **采信**（`判定依据` 须写明算法）；
  前置信号缺失（如无 `floor_scale`）→ **待确认**，**不得借"孤立"名义放行**。
- **禁止为比对自创算法** —— 比对实现**唯一入口**（`ftth_common`）；新比对逻辑须过**含已知错误样本**的回归
  （只在"应通过"样本上跑绿**不算验证**）；会话内禁止临时写比对脚本。

### 5.8 「已确认」与「已定案」是两个词，不得混用（2026-09-18 立）

| 词 | 依据 | 出处 |
|---|---|---|
| **已确认** | 用户在**本会话**的**原话** | SKILL.md L0-I3 防伪条款 |
| **已定案 / `settled`** | **系统自洽**（总体核对通过，或用户裁决） | SKILL.md L1-C8 状态契约 |

**"单源基本和确认一样"指的是效力，不是依据** —— 交付文本写"已确认"必须能引用户原话；
单源值经总体核对通过的写 **`settled`（已定案）** 并注明依据为"自洽核对"。
两者混用会让 L0-I3 防伪条款失效（什么都成了"已确认"）。


## 五·补 证据来源等级（2026-09-18 立，与 SKILL.md L1-C9 配套）

来源冲突时按等级取信。**设计要点三条，均来自本技能实测教训，勿简化**：

| 等级 | 来源 | 说明 |
|---|---|---|
| `E-DXF-TEXT` | DXF TEXT/MTEXT 实体直读 | 图上原样，最高一档 |
| `E-DXF-GEOM` | DXF 几何计算 / INSERT 块属性 | 图上原样，最高一档 |
| `E-PROC` | 程序推导（V 型 / 断口 / 区间法 / 图标计数） | 次高，须带方法与证据 |
| `E-IMG` | 视觉模型 OCR | **只能用于发现疑点，不得覆盖 `E-DXF-*`** |
| `E-HUMAN-RULING` | 用户**本会话**的明确裁定（＝I5-A） | **最高**，覆盖其余全部条款 |
| `E-HUMAN-GUESS` | 人工肉眼判读 / 推测 | 最低，仅作线索 |

- **`E-DXF-TEXT` 与 `E-DXF-GEOM` 之间无全序** —— 谁优先由**场景规则**定，不搞一刀切。
  现成反例：箱位来源「以图形符号开头才可信，编号文字为回退值」⇒ 该场景下 `E-DXF-GEOM` > `E-DXF-TEXT`。
- **「人工」必须拆成两级**：`E-HUMAN-RULING`（裁定，最高）与 `E-HUMAN-GUESS`（肉眼推测，最低）。
  笼统把人工定为最低，会与 I5-A「用户裁定覆盖其余全部条款」**直接打架**。
- **低等级不得覆盖高等级**，只能用于发现疑点 —— 与 §5.1 归一化硬边界 1 同一思路：
  「长得像」不等于「语义等价」。
- 与 §5.4「数据来源权威等级」的关系：§5.4 是**项目方声明的来源优先序**（空表即按第④类），
  本节是**证据形态的等级**。两者都非空时**以 §5.4 的声明为准**（声明是规则，不是推理）。

- **同等级内部再分档（A′/B′，2026-09-19 立）**：某一 `E-DXF-*` 等级内按「信息齐备度」再分档时，分档**必须登记进本表**（写明所属等级、形态、相对既有等级的优先级）；**未登记的档不得在代码里生效** —— 教训：新档未登记即生效，覆盖了更高档既有的归属（P0 回归）。实例：箱位直写属 `E-DXF-TEXT`，下分 A′（楼栋+单元+安装层三者齐备）/B′（只到单元，安装层仍交区间法）。
- **新档 / 低档只补空缺，不改写归属**：只用于填补「无归属」的空缺，**不得改写已有归属**；已有归属来自更高档证据时尤其如此 —— 改写即静默择一，等同违反 §5.6 底线 1。


## 六、已确认理解必须落盘（治「重启式梳理」）

**规则**：每完成一个阶段（探查判定 / 解析 / 覆盖 / 户数），把**已确认的理解**写进
`.temp/<项目>/理解快照.json`，每项至少带三个字段：

| 字段 | 内容 |
|---|---|
| 值 | 如「3#楼 → 2 单元 → 刻度列 x≈<本图实测值> → FX07# → 每层 2 户」 |
| **来源** | 哪个读数 / 哪条命令 / 哪条标注得来（可复现） |
| **状态** | `已确认` / `待裁决` / `已裁决`（含裁决人） |

**下一阶段先读它；未变更的项不得重新推导。**

理由（实测）：长任务里「重新建立全局理解」的推理占**全部推理字符的 26.3%**（对照：
一次性把待裁决项列表交人的会话仅 **6.7%**）。根因不是模型笨，是**已确认的理解没有落盘** ——
换一个视角（看箱、看覆盖、看户数）就只能把全局重建一遍。落盘后这一步从「重推」变成「读文件」。

**载体**（`scripts/ledger_state.py`，**不要手拼 JSON**）：

```
ledger_state.py snapshot-set --project-dir D --key K --value V --source S [--status 已确认]
ledger_state.py snapshot-get --project-dir D [--key K]     # 每阶段开工先无参跑一次
```

字段结构由脚本固定，跨阶段 / 跨会话一致；手写 JSON 会出现字段漂移，下一阶段读回来还得重新解释一遍。
`--source` **必填** —— 没有来源的条目无法判断「是否仍然成立」，下一阶段只能重推。

## 七、人工裁决的接收与落盘

拿不到人工裁决时容易反复推演，拿到之后又容易重复推演 —— 两条都要堵：

1. **一次锁定，不再复议**：收到人工裁决后，该问题**不得再次列为待确认项**，
   也不得再推演「是否应该这样处理」。裁决即基准值（同 L0-I4 ⑤、I5-A）。
   实测反例：收到「乘数按相乘处理」后，又推了数段去问「是哪一列要乘」——
   规则早已写明「用户裁定覆盖其余全部条款」，是执行没跟上。
2. **执行前落到作用对象与粒度**：收到「按 N 处理」这类裁决，须先把它落到
   **具体作用对象与粒度**上 —— 是「**每个图标 = N**」还是「**该楼总数 = N**」。
   把两种解释并列写清后，**若仍有歧义，按 §5.5 追问一次**；
   **不得自行选一种执行**（自选即是把裁决权收回自己手上）。
3. **裁决须项目级落盘**：写入 `.temp/<项目>/裁决台账.json`
   （问题 / 裁决原文 / 裁决人 / 时间 / 适用范围）。
   **只在会话对话里出现的裁决不算落盘。**
   实测依据：同一项目在两个通道（GUI 会话与 IM 会话）并行时，A 通道收到的裁决
   B 通道完全看不到，导致同一张图两次交付相差 122 户（其中 120 户正是"该不该乘"）。
   通道之间不同步是常态，**落盘是唯一能让裁决跨通道生效的方式**。

4. **载体**：`ledger_state.py ruling-add --project-dir D --question Q --ruling R --by X [--scope S] [--key K]`。
   `--by`（裁决人）**必填** —— 没有裁决人的「裁决」不算落盘。
   显式给 `--key` 时才联动同名快照项状态 → `已裁决`；**不自动匹配**（自动匹配＝静默改状态）。

## 八、原始写法与别名台账（归一化的出口）

归一化要能"只用于比对、不回写"，前提是**原始写法有落点**。落点两条：

| 落点 | 内容 |
|---|---|
| **别名台账** | `.temp/<项目>/别名台账.json`：`{canonical_id, raw_labels[], 判据(坐标/连线), 状态}`，状态用 `已确认` / `待裁决` |
| **成品列** | 标准地址表的**别名 / 备注列**（模板已预留）。台账里 `已确认` 的别名写进对应行；`待裁决` 的不写，列入待确认项 |

规则：

- 台账里每个 `canonical_id` 的判定依据**必须可外部复核**（坐标邻近 + 连线关系），
  不允许出现"因为看起来像"这类依据（同 §5.1 硬边界 2）。
- 同一 `canonical_id` 下若出现**两个不同物理体**的写法 ⇒ 立即拆开并按 §5.3 第④类报人。
- **别名列 / 备注列为空是合法的**（本图无异写时本就该空）；但"算出了异写却没写进去"
  属出口缺失 —— 与"算出的结论没出口"是同一类问题。

**载体**：

```
ledger_state.py alias-add --project-dir D --canonical C --raw r1,r2 --evidence E [--status 已确认]
```

标 `已确认` 时 `--evidence`（判据）**必填**；若某原始写法已挂在别的 `canonical_id` 下，
**脚本拒绝写入并返回 rc=2**、只提示报人 —— 即 §5.3 第④类，**不自动择一**。

## 九、三本台账的汇总与自检（出口门禁）

| 命令 | 用途 | 退出码 |
|---|---|---|
| `ledger_state.py pending --project-dir D [--md out.md]` | 汇总全部 `待裁决` 项，按 **C5 四列**打印；`--md` 另存为可直接提交的表 | 0 |
| `ledger_state.py check --project-dir D` | 三本台账一致性自检 | 有未裁决项 / 别名归属冲突 → **2**；仅警告 → 0；未初始化 / 台账损坏 → 3 |

自检项：未裁决项 · 缺裁决人 · 缺来源 · 标 `已确认` 却无判据 · 同一原始写法挂到两个 `canonical_id`（归属未定）。

**`init` 的语义是"补建"不是"重置"**：三本台账已存在时原样保留、不清空；
台账不存在时报「未初始化」并给补救命令，**不隐式建空文件** ——
「从未落盘」与「落盘了但为空」是两件事，混同会把前者伪装成后者。

| 台账 | 文件名 | 条目形态 | 写入方式 |
|---|---|---|---|
| 理解快照 | `理解快照.json` | 按 key 索引（dict） | 同 key 覆盖，保留 `历史` |
| 裁决台账 | `裁决台账.json` | 按序追加（list） | 只增不改 |
| 别名台账 | `别名台账.json` | 按序追加（list） | 只增不改 |

> 与 `ledger_elements.py`（**图侧**元素台账：图上有哪些元素、各在哪，只读）区分：
> 本节的台账是**会话侧**状态记录，随作业推进而增长。两者同名不同物，勿混。
